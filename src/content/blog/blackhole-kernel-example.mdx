For my own clarity and as an improvement to the previous blackhole architecture blog—which went over the chip from a more abstract, tt-metal pov—this blog will cover the different ways you can write an RMSNorm kernel on a Tenstorrent blackhole chip. I've learned a lot more about the chip since the last article, and there are a lot of constraints, rules, and oddities that we need to be aware of when deciding how to lower kernels. 

By lowering kernels I mostly mean splitting an operation into a dependency chain, deciding which parts can be executed simultaneously, and whether a part should be run using SFPU or FPU operations. A few reasons to choose each one: 

- the SFPU can run precise float32 arithmetic. 
- the FPU is limited to tf32 / bfloat16 operations
- FPU re-use is limited; you have to run `MOVD2A` in order to transfer FPU accumulations back to srcA/B. 
- the FPU is four to sixty-four times faster than the FPU, across all operations

The approach I've come up with starts with picking the most precision-maximizing lowering, then moving as many operations to the FPU as possible before the relative-error becomes too high for accurate inference. Usually I try to match what a GPU would produce by default. In some cases you'll have code like

```python
class RMSNorm:
  def __init__(self, dim:int=2048, eps=1e-5):
    self.eps = eps
    self.weight = Tensor.ones(dim) # not real weights.

  def __call__(self, x:Tensor) -> Tensor:
    # for simplicity: x.shape=(2048,)
    dtype = x.dtype # store original tensor dtype
    xf = x.float()
    x = (xf * (xf.square().mean(axis=-1, keepdim=True)+self.eps).rsqrt()).cast(dtype)
    return x * self.weight
```

which explicitly makes most of the rmsnorm compute in float32. If you omit `xf=x.float()`, you'll end up with inaccurate inference. This is the operation we'll lower to a blackhole kernel.

Formally written:
$$
  \operatorname{RMSNorm}(\mathbf{x})
  =
  \boldsymbol{\gamma} \odot
  \frac{\mathbf{x}}
  {\sqrt{\frac{1}{d}\sum_{i=1}^{d} x_i^2 + \epsilon}}
$$ 
((where γ is the weight, x is the input activation, d is 2048, and ε is `1e-5`.))

We won't fully respect the `.cast()` and dtypes in the tinygrad example above, but our example will have high enough precision to be viable as part of a model inference stack. 

You can split RMSNorm into a few independent operations (this will matter later when we overlap FPU and SPFU operations):
$$
  \begin{aligned}
    \mathbf{w} &= \mathbf{x} \odot \boldsymbol{\gamma}
    && \text{(weighted input)} \\[6pt]
    r &= \frac{1}{\sqrt{\frac{1}{d}\sum_{i=1}^{d} x_i^2 + \epsilon}}
    && \text{(inverse RMS)} \\[6pt]
    \mathbf{y} &= \mathbf{w} \cdot r
    && \text{(scaled output)}
  \end{aligned}
  $$

## getting data in and out of the SFPU
There are two sfpu load/store instructions, `SFPLOAD` and `SFPSTORE`. Both load and store only to `dst`, the big 1024x16 shared sfpu/fpu register. The way it loads and stores is exceptionally weird, take a look:

## getting data into dst
Every kernel's inputs start in DRAM ((the 8 GDDR6 banks)). For RMSNorm, that's two tensors of 2048 bf16s: the weights γ and the activation x. They take two hops to reach dst.

1. DRAM -> L1: brisc issues the NoC reads that pull both tensors into the core's L1.
2. L1 -> dst: trisc0 drives the unpacker ((by convention. this is not enforced by hardware; any trisc has full access to the entire coprocessor.))

Once x and γ are in dst, we can start issuing SFPU instructions on trisc1. 

### where things go in dst
As shown in the [tldraw](https://www.tldraw.com/f/CTUj3aHH-vm4jNhulJDp4?d=v-162.-479.4272.3991.page) diagram, dst is normally 1024x16, but we always keep float32 elements in it, which halves the size to 512x16. You can think of that as 64 allocations of 128 elements (8x16) each. Every FPU op accumulates into one contiguous 8x16 block, so it's the natural unit for planning layouts. 

For this kernel, we can fit x in `dst[0:2048]` (allocations 0-15) and γ in `dst[2048:4096]` (16-31) leaving the bottom half free for intermediates. When the kernel gets larger, we have to start streaming data from DRAM and streaming data out, since the entire computation can't fit inside the FPU's internal registers. We'll revisit that case later. 

## inverse root mean squared (RMS) on sfpu 

### square and average 
$$
s = \sum_{i=0}^{2047} x_i^2,
\qquad
m = \frac{s}{2048} + \epsilon,
\qquad
r = \operatorname{rsqrt}(m).
$$

We can save some instructions and compute time here by squaring and summing at the same time. There are roughly two kinds of SFPU instructions; the first kind takes two source registers and one output register where the computation's output will be stored, and the second one modifies a register in-place. The `SFPMAD` ((multiply **ad*d)) instruction takes three arguments:

```py
TTSFPMAD(Lreg0, Lreg1, Lreg2, Lreg3, instr_mod1=0) 
``` 

and computes LReg0 * Lreg1 + Lreg2 and **stores into** Lreg3.

Initialize all 32 lanes of L0 to FP32 zero, then run a loop:
1. Load 32 elements from dst into L1. 
2. Issue `TTSFPMAD(L1, L1, L0, L0)`. This is `x*x + prev_sum = new_sum`

The weird load/store addressing of the SPFU doesn't matter here, since the order of the elements doesn't make a difference; the sum will be the same no matter what order you compute it in. We just have to make sure the loads go through the entire 2048-element allocation of x in dst. This takes $\frac{2048}{32}=64$ loads, where alternate between even/odd copies and alternate between loading even vs odd elements. 

After this sequence, you end up with 32 partial sums in L0. The Lregs are summed elementwise; imagine stacking two Lregs on top of each other and adding down, that is what ends up in L0. Now we have to sum all 32 lanes in L0. 

Up until now, all the SPFU instructions we've run have interpreted a Lreg as a flat list of 32 floats. To do a sum of elements within a register, we need to look at the register like a grid of 4 rows and 8 columns. 

<SfpuReduction client:visible />

First, we reduce every row of 8 into its own sum. Since you can only do sums *between* Lregs, we have to rotate the 2nd lreg and keep summing until every item in lreg sees every other item. 

After you have the row sums in L0, copy that to 3 other Lregs. Then you run `SFPTRANSP` (no arguments). The 4 0th rows (l0's 0th row, l1's 0th row, etc) move to l0. Same for the 1st, 2nd, and third rows. 

Now, you can just add across all 4 Lregs using `SFPADD`. Oddly, `SFPADD` and `SFPMAD` are the same thing, but the ISA docs recommend that you use SFPADD if you're multiplying by one, i.e, Lreg0 is 1 (this makes our SFPMAD just an ADD). In this case our instruction would look like: 

`TTSFPADD(Lreg10, L0, L1, L0) # L0 <- L0 + L1`

Repeated 3 times to add l1, l2, and l3 to l0. 

At this point, our sum is repeated in every lane inside L0. Next is just `SFPMUL` by $\frac{1}{2048}$, then another `SFPADD` to add ε `1e-5`. 

To multiply by a constant, like in our `SFPMUL` example, we must load the immediate constant value into an Lreg. This is done using `SFPLOADI`: 

`SFPLOADI(destination, mode, immediate_16_bits)`

Every load requires two `SFPLOADI` instructions, because there is only enough room in the 32-bit instruction encoding to supply 16 bits at a time.  `bits & 0xffff` to load the lower bits, and `bits >> 16` to load the upper bits. 

The remaining computations are the x * γ, rsqrt(the above sum), then the 2nd elementwise with the result of the rsqrt. 

> note: the reason we use l0-l3 here is because `SFPTRANSP` only works on l0-l3 or l4-l7. we could have used l4-l7. 

### rsqrt (fast inverse square root)
Currently, L0 in the SFPU holds 

$$
x = \frac{\sum_i x_i^2}{2048} + \epsilon
$$

and we need to calculate 

$$
\frac{1}{\sqrt{x}}
$$

A reciprocal square root means

$$
y=\frac{1}{\sqrt{x}}=x^{-1/2}.
$$

Using logarithms, powers become multiplication:

$$
\log_2(y)=\log_2\left(x^{-1/2}\right)
=-\frac12\log_2(x).
$$

In log space, computing $1/\sqrt{x}$ is simple:

1. Compute $\log_2(x)$.
2. Divide it by 2.
3. Negate it.
4. Convert back from log space:

However, blackhole does not have a `log2` instruction. Fortunately, it turns out that the bit pattern of a float can be exploited to approximate one. 

For a positive float:
<Float32Bits />

$$
x = \left(1 + \frac{M}{2^{23}}\right) \cdot 2^{E-127}
$$

Shifting the entire float32 right 1 bit is an approximation for the log computation above (you subtract this from the constant `0x5f1110a0` to do the negation). ((this requires some math, have chatgpt explain it to you. there is also [a paper](https://arxiv.org/html/2307.15600v1) on that constant and the algorithm used here))

The SFPU instructions for this are straightforward, you just need:

```
SFPSHFT(0xfff, ZERO, L1, 1) # shift the entire 32-bit pattern right by one
# load magic constant into an lreg
SFPLOADI(L2, 10, 0x10a0)   # lower 16 bits
SFPLOADI(L2,  8, 0x5f11)   # upper 16 bits

# l1 = L2 - L1
SFPIADD(0, L2, L1, 6) # integer subtraction; modifier 6 also preserves lane flags
```

We then measure how far away our approximation is from the correct answer:

$$
my^2 = 1
$$

For example, with $m=4$ and the rough guess from above: 

$$
y_0 = 0.408330
$$

we get

$$ 
z = my_0^{2} = 4(0.408330)^{2} \approx 0.6669
$$

Since $z < 1$, we must optimize. The first correction is a cheap polynomial correction applied to $y_0$: ((again: read the paper if you're curious, this is not really the point of the article.))

```
t = -m * y * y
p = 2.2825186 + t * (2.2533049 + t)
y = y * p
``` 

Which we can evaluate using SFPMUL, SFPADD, and SFPMAD. Now we have $y_1 \approx 0.50000593$.

The next correction is the newton correction, which builds on $y_1$:

```
error = 1 - m * y * y
y = y + (0.5 * y) * error
```

Now we have the final rsqrt approximation: $y_2=0.5$ in Lreg 0.

## elementwise multiplications

The last computation remaining is simply

$$
x \odot γ \odot y_2
$$

```
SFPLOAD  → L1 = next 32 elements of x
SFPLOAD  → L2 = corresponding 32 weights γ
SFPMUL   → L1 = L1 × L0 # l0 contains inverse rms
SFPMUL   → L1 = L1 × L2
SFPSTORE → write L1 back to dst[4096:6144]
```

Repeated until we cover all 2048 elements.

For lane i, that computes: 

$$
L1_i \leftarrow (x_i \cdot r)\cdot\gamma_i
$$

## packing the final output

Now we can run the packer using trisc2, copy from `dst[4096:6144]` to L1, and then use ncrisc to copy that back to DRAM.
